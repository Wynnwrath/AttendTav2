# AttendTa MVP database setup

This guide uses the PM-approved `new mvp.sql` schema as its source. The tracked,
executable copy is `database/attendta-mvp-schema.sql`. The local source under
`docs-local/` is gitignored, so teammates should use the tracked database script.
All paths below are relative to the repository root (the folder containing
`AttendTa.sln`). For example, if the repository is cloned to
`C:\source\AttendTa`, the schema script is
`C:\source\AttendTa\database\attendta-mvp-schema.sql`.

## Safety and scope

- These instructions create/reset only a local disposable database named
  `AttendTaMVP_Test` on `(localdb)\MSSQLLocalDB`.
- Do not run the reset script against shared, staging, or production databases.
- Existing `AsiBasecodeDB` records are not migrated. The reset script does not
  touch `AsiBasecodeDB`.
- `database/seed-local-admin.sql` creates the local test admin `admin@gmail.com`
  with role `admin` and active status. The password hash must be generated by the
  Auth implementation and supplied at run time; the script does not store a
  plaintext password or precomputed hash. Keep local test credentials out of the
  repository and never use them outside a disposable local database.
- A test account is needed before exercising rows with required `created_by`
  foreign keys or member `user_id` links.

## Requirements

- Windows with SQL Server LocalDB installed.
- SQL Server Management Studio (SSMS), or `sqlcmd`.

## Setup in SSMS

1. Open SSMS and connect with Windows Authentication to:

   ```text
   (localdb)\MSSQLLocalDB
   ```

2. Open `database/reset-local-mvp-test-db.sql` and execute it. This drops and
   recreates only `AttendTaMVP_Test`.
3. Open `database/attendta-mvp-schema.sql`.
4. Select `AttendTaMVP_Test` as the query window database and execute the file.
   The script checks the current database name and refuses to run elsewhere or
   when the schema already exists.
5. Refresh Object Explorer and confirm the ten MVP tables were created.
6. Have the Auth implementation generate a hash for the local test password.
   In PowerShell, pass the generated hash (not the password) to the seed script:

   ```powershell
   $env:AdminPasswordHash = Read-Host "Paste Auth-generated password hash"
   sqlcmd -S "(localdb)\MSSQLLocalDB" -E -d AttendTaMVP_Test -b -v "AdminPasswordHash=$env:AdminPasswordHash" -i "database\seed-local-admin.sql"
   Remove-Item Env:AdminPasswordHash
   ```

   Confirm the script returns one active `admin@gmail.com` account.
7. Open `database/seed-event-types.sql` and execute it in `AttendTaMVP_Test`.
   It inserts the six starter event types if they are missing and sets
   `created_by` to `admin@gmail.com`'s `user_id`.

To run the application against this disposable database, set the connection
string only in the local PowerShell session before starting the app:

```powershell
$env:ConnectionStrings__DefaultConnection = "Server=(localdb)\MSSQLLocalDB;Database=AttendTaMVP_Test;Trusted_Connection=True;MultipleActiveResultSets=true;TrustServerCertificate=True"
$env:DOTNET_ROLL_FORWARD = "LatestMajor"
dotnet run --project "ASI.Basecode.WebApp\ASI.Basecode.WebApp.csproj"
```

This environment override is temporary; it does not edit the tracked
`appsettings.json`. Close that PowerShell session to clear it. The app uses
ASP.NET Core's default configuration ordering so environment variables override
JSON settings.

Venue photos are stored outside `wwwroot` under
`<Common:SetupRoot>\uploads\venues`; the database stores a relative path such as
`venues/<generated-name>.png`. The default `Common:SetupRoot` in
`appsettings.json` is machine-specific. Set it to a writable, persistent path
outside `wwwroot` before testing uploads. The current implementation accepts
JPEG and PNG photos up to 5 MiB.

## Setup with `sqlcmd`

Run these commands from the repository root:

```powershell
sqlcmd -S "(localdb)\MSSQLLocalDB" -E -d master -b -i "database\reset-local-mvp-test-db.sql"
sqlcmd -S "(localdb)\MSSQLLocalDB" -E -d AttendTaMVP_Test -b -i "database\attendta-mvp-schema.sql"
# First generate the local test password hash through Auth (never pass plaintext here).
$env:AdminPasswordHash = Read-Host "Paste Auth-generated password hash"
sqlcmd -S "(localdb)\MSSQLLocalDB" -E -d AttendTaMVP_Test -b -v "AdminPasswordHash=$env:AdminPasswordHash" -i "database\seed-local-admin.sql"
Remove-Item Env:AdminPasswordHash
sqlcmd -S "(localdb)\MSSQLLocalDB" -E -d AttendTaMVP_Test -b -i "database\seed-event-types.sql"
```

## Verify the schema

In SSMS, select `AttendTaMVP_Test` and run:

```sql
SELECT name
FROM sys.tables
WHERE is_ms_shipped = 0
ORDER BY name;

SELECT name, is_unique, has_filter, filter_definition
FROM sys.indexes
WHERE object_id = OBJECT_ID('dbo.account_requests')
  AND is_hypothetical = 0
ORDER BY name;
```

The second query should show the filtered `created_user_id` index and pending-only
unique indexes for email and student number. The schema script also creates
filtered unique indexes for nullable QR tokens and certificate numbers.

## Legacy local database

There is no data-transfer migration in this MVP setup because existing local
records do not need to be retained. Keep `AsiBasecodeDB` as a fallback while
testing `AttendTaMVP_Test`. Once the MVP database is verified, update the local
connection string as shown above. If you later choose to remove the old local
database, back it up and verify its name before deleting it manually; the reset
script intentionally never drops `AsiBasecodeDB`.

## Current limitations

The existing application login is a stub and does not provide a valid persisted
user ID. Consequently, full create-flow testing that requires `created_by` or a
member's `user_id` depends on the Auth/account-request integration and a
disposable test account. Do not use a hard-coded production user ID to bypass
those foreign keys.
